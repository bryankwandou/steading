Steading

Save video, audio and photographs from the web onto your own machine. The program runs on your computer, so no file and no link is ever handed to a third party.

steading.vercel.app · 1,752 sites · 12 formats · 24 languages

The problem

Every other downloader takes your file somewhere first.

A site that fetches on your behalf must, for a moment, hold the thing you asked for. It sees the link, it sees the file, and it sees you. That moment is not visible from the page, and there is no way for you to check what happens in it.

For most people that is a nuisance. For a journalist saving evidence, a student keeping coursework, or anyone in a place where the wrong link is dangerous, it is the whole problem.

  • Your link is read by a stranger's server
  • Your file passes through it
  • An account is usually required
  • A queue, a limit, an upgrade prompt

The solution

Remove the middle step by removing the middle.

The program runs on your own computer. The file is written straight to your disk by software you control, so there is no moment when anyone else is holding it.

0bytes sent to anyone else
0accounts required
0npm runtime dependencies

The last figure is not a boast about tidiness. Zero dependencies is what makes the privacy claim checkable: there is no third-party package that could be sending anything, so the claim can be verified by reading the code rather than trusted.

How it works

Paste a link. Choose what to keep. It writes to your disk.

  1. Look first. The link is read to find what is actually there — length, available heights, whether a video track exists. No bytes are downloaded yet.
  2. Choose the kind. Video, audio or photo. Anything the post cannot provide is disabled rather than left to fail when pressed.
  3. Choose the shape. Twelve formats, and for photographs a five-step slider trading size against fidelity.
  4. It is yours. An ordinary file in an ordinary folder, which still opens when this page is gone.

Not one source

Three independent ways to find a file.

An auditor recorded the single-source dependency as a high risk and was right. The remedy is a chain of independent sources, none of them required — not hundreds of per-site packages, which would trade one well-tested source for many unmaintained ones.

1yt-dlp≈1,750 per-site extractors under one test suite
2streamlinkA separate project, so it fails on a different set of sites
3the page itselfNo binary, no package. Cannot be uninstalled.

Proved with the primary source switched off: VIDEO_PROVIDERS=scrape returns extractor: page on pages yt-dlp rejects outright.

What it does not do

The limits, stated rather than found.

  • Instagram carousels. A fourteen-photo post returns its cover. The rest needs a signed-in session, and this program never asks for an account.
  • Video and audio on the website. Merging streams needs ffmpeg and a seekable disk, which a hosted function has neither of. Those run on your machine.
  • Three sites were dropped. Douyin needs cookies, Rumble returned 403 to every probe, Vidio's segments 404. The list says 22, not 25.

This slide exists because a panel will find these anyway. A submission that lists its own gaps can be checked; one that hides them only has to be caught once.

The interface says the same thing in place: a one-picture result explains that the site publishes only its cover to visitors who are not signed in, rather than leaving a thin answer looking like a fault.

Reach

Built for the phone someone actually has.

12formats across video, audio, photo and PDF

Zero dependencies is also why it installs on a phone: npm install in Termux is slow and fragile, and a folder that runs with node server/index.js does not need it. The application shell is a few tens of kilobytes and works offline once loaded.
